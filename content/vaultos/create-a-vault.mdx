# Create a vault

A business creates a vault by choosing its name and its symbol. The factory deploys the contract and chooses the address. The vault starts empty. The wallet that asks for the vault signs the creation. The product does not take the private key.

## What is set at creation

| Field | Rule |
| --- | --- |
| Vault name | Required. 1 to 64 bytes. This is the name a holder sees. |
| Share symbol | Required. 1 to 16 bytes. This is the ticker on the share. |
| Asset | The one asset the factory is built for. Creation does not substitute a different token. |

The limits, and what the name does not decide, are on [Name and symbol](/concepts/name-and-symbol). The vault itself is on [The vault](/concepts/vault).

## What creation does

The factory records the vault address, the underlying asset, the wallet that asked for the vault, and the name and symbol. It does not move the asset into the vault. Value moves later, when a holder deposits.

After the creation transaction is included, the registry checks it. A vault is listed only when that check passes. The checks are on [Registration](/vaultos/registration).

If the transaction confirms and registration fails, the vault can still exist on the chain. The registry’s reason is the record of that failure. Creating again with the same name deploys another vault. It does not repair the failed registration. Sending a creation hash that is already stored returns the existing record and does not add a second one.

If the wallet rejects the request, nothing is deployed and nothing is listed.

## Before this can lock

Three decisions are still open. None of them is chosen.

- Which asset the vault holds, and who may mint it. Supply of that asset is controlled.
- How far white-label goes beyond the name and the symbol.
- Whether the API is a shared service, or a deployment for each business.

The first release still creates a vault the same way: a name, a symbol, one controlled asset, a signature, and then the registration check.
